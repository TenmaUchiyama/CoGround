# CoGround と TidyBot・That's Mine の比較

作成日: 2026-11-19
根拠:
- CoGround: `grounding_server` のコード（`llm/compile_rule.py`、`norms/evaluate.py`、`norms/planner.py`、`norms/task.py`、`executor.py`、`vlm.py`、`detection.py`、`taxonomy.py`）とREADME
- TidyBot（Wu et al., IROS 2023 / Autonomous Robots 47(8)）、That's Mine（Tan, Brawer & Scassellati, AAAI 2019）: 原文を再読した `search/I1_crossread.md`

## 1. 処理の流れの比較

| 段階 | That's Mine (2019) | TidyBot (2023) | CoGround |
|---|---|---|---|
| ルールの入り方 | 実行中の叱責（「それは私のだ」）、または許可・禁止の例から帰納 | ユーザーの配置例（数個）をLLMが要約 | 住人の言葉をLLMが変換（`norms.compile`）。範囲や時刻が決まらないものは保留にして住人が確定 |
| ルールの形 | 述語のホーン節（例: `forbid pickUp if ownedBy any`） | 要約文 →「カテゴリ → 収納先」の対応と、置く／投げ入れるの選択 | R = (N, S, T, C=(W, φ))。義務・禁止・許可、効く場面（時刻・依頼者・子供が近いなど）、対象、計画のどこを調べるか、何を要求・禁止するか |
| 規範の種類 | 禁止と許可（所有にもとづく） | 収納先（義務に近い）と操作の種類のみ。禁止はない | 義務・禁止・許可＋例外（`exception_of`）＋台車の進入禁止・停止 |
| 事実の推定 | **所有者を位置・色・接触時間から確率的に推定**（中心的な貢献） | CLIPで物体をカテゴリに分類 | 推定しない。属性は検出器・Unity・（未実装の）VLMから受け取り、住人が訂正できる |
| 依頼 | 片付け、または単発の命令 | 片付けのみ | ルールとは別の依頼（`task.request`）。LLMが対象物体を決め、物体ごとの行を作る |
| 判定 | 確率の閾値で行う／行わない | 必ずどこかのカテゴリに分類 | 物体×ルールごとに、違反／適合／適用外／**未確定（不足事実つき）** |
| 実行できない物 | 所有物は飛ばして残りを片付ける | 想定なし | 理由つきで保留し、残りは計画・実行（「2点中1点」） |
| 置き場所 | — | 収納先の位置は固定 | 収納先の空きを順番に確かめ、空きがなければ動かさない |
| 実行後 | — | — | 置いた後に観測して完了／別の場所／未確認を記録。台車の移動中は進入禁止と子供の接近を監視 |
| 訂正 | 叱責から学び直す（オンライン学習） | — | 属性・スコープ・領域・例外を訂正し、判定の変わった項目を差分で返す |
| 実行前の確認 | — | — | ARで計画と理由を表示 |
| 評価 | 実機の定性デモ3場面＋シミュレーションの定量（ルール精度） | テキストのベンチマーク（未見物体で91.2%）＋実機（未見70物体で85.0%） | 単体テストのみ。対照付きの評価はまだない |

## 2. CoGroundで増えていること

例: 住人が次のように教えておく。
- 「割れ物には触るな。ただし私が頼んだときはいい」
- 「皿は食器棚の上段、コップは下段」
- 「18時以降はリビングに入るな」
- 「子供が近くにいる間は止まれ」

その後、「机の上を片づけて」と頼む。

| できること | That's Mine | TidyBot | CoGround |
|---|---|---|---|
| 1. 禁止・義務・許可を同時に扱う（割れ物の禁止と皿の収納先） | 禁止・許可のみ | 収納先のみ | ○ |
| 2. 時刻・依頼者・状態でルールの効く範囲を変える | 所有者が依頼すれば許可（依頼者に近い仕組みは場面2にある） | × | ○（時刻・依頼者・子供の接近） |
| 3. 「ただし私が頼んだら」という例外を、元の禁止と結び付ける | 所有の主張で許可が変わる（近い） | × | ○（`exception_of`） |
| 4. 割れ物かどうか分からない皿で、触らずに保留し「割れ物か」だけを尋ねる | ×（確率で行動） | ×（必ず分類） | ○（未確定＋不足事実） |
| 5. その皿を保留したまま、ほかの物は片付け、何が残ったかを理由つきで報告 | 一部（所有物を飛ばす） | × | ○（物体ごとの行と理由） |
| 6. 計画の途中（つかむ時点、台車の移動中、置き終わった時点）ごとにルールを調べる | × | × | ○（W） |
| 7. 置いた後に観測して、本当に収納先にあるか確かめる | × | × | ○（予測と観測を区別） |
| 8. 範囲があいまいなルールを、勝手に補わず住人に確定させる | × | × | ○（保留して確定） |
| 9. 実行前に、ARで計画と保留の理由を見せる | × | × | ○ |

**ここまでの結論**: この2本と比べると、CoGroundはルールの表現力、不確かさの扱い、部分実行と報告、実行後の確認、訂正、実行前の確認のすべてで、できることが増えている。

## 3. CoGroundにできない、または弱いこと（正直な比較）

| 項目 | 相手が持っている力 | CoGroundの現状 |
|---|---|---|
| 例からの汎化 | TidyBot は、数個の配置例から「服はベッドへ」のような規則を要約し、未見の物体に当てはめる（常識だけの45.6%に対して91.2%） | 住人が明示的に言ったルールしか使わない。暗黙の好みを例から推定しない |
| 事実の推定 | That's Mine は、所有者を位置・色・接触時間から推定する。ここが論文の中心 | **属性のキーは固定されていない**（`attributes: dict[str, Attribute]`、値は bool/int/float/str、`Target.matches` と `objects.set_attribute` は任意のキーを受け付ける）。`taxonomy.ATTRIBUTES` の6語はLLMとVLMに見せる既定の語彙で、サーバー側の制限ではない。したがって `owner = alice` のような属性とルールは表現できる。欠けているのは、その値を**推定する部品**（所有者を推定するものがない）と、「物体の所有者＝依頼者」のような変数の結び付け（`scope.requester` は固定の人物IDとの一致のみ） |
| 叱責からの学習 | That's Mine は、実行中の「それは私のだ」1回から規範を学ぶ | 訂正はできるが、実行中の叱責から新しいルールを作る仕組みではない |
| 開かれた語彙 | TidyBot は CLIP で要約したカテゴリ名に分類する | 検出は YOLO-World（開かれた語彙）だが、LLMはカテゴリ表と属性の語彙から選ぶ |
| 属性の認識 | TidyBot は実機で画像から分類している | 属性は Unity の正解か mock。`vlm.py` は off と mock のみで、本物のVLMは未実装 |
| 定量評価 | 両方とも数値がある | まだない |

## 4. 分野全体で見たときの位置づけ

2本だけと比べると「増えている」が、個々の機能は2024〜2026年の別の研究にある（詳細は `HouseRule_Novelty_Report.md`）。

| CoGroundの機能 | 同じ機能を持つ研究 |
|---|---|
| 義務・禁止・許可＋条件の構造 | AgentSpec、ODRL、ADICO |
| 物体ごとの制約チェック | RoboGuard、AgentSpec |
| 一部だけ実行する | RuleGraph |
| 不足事実で保留して質問 | SafeGate（ただし依頼全体を保留） |
| ルールごとの判定（満たす／違反／適用外） | VFM（ただし「判断できない」を「適用外」にまとめる） |
| 時間で効くルール | Safety Chip、RoboGuard（LTL） |

したがって、論文で言えるのは「新しい仕組み」ではなく、「家庭の住人が教えるルールという設定で、これらを1つのシステムにまとめ、物体ごとに未確定を扱えること」と、それを測る評価である。

CoGroundにしかない振る舞いとして、実装で確認できたもの:
- 「★の物に18〜22時は触るな」で★が不明なとき、10時なら適用外として片付け、20時なら★の有無だけを尋ねる。
- 「aliceが頼んだとき以外は★に触るな」で依頼者が不明なとき、依頼者だけを不足事実として返し、ほかのルールの判定には影響しない。

これが既存手法（1物体を1単位にしたRuleGraph、依頼全体を保留するSafeGateなど）で再現できないことを、実験で示す必要がある。

## 5. 差を強める方向

1. **That's Mine の強みを取り込む**: 実行中の「それは触らないで」から、ルールを提案して住人に確定させる（いまの保留→確定の流れに乗せられる）。
2. **TidyBot の強みを比較条件にする**: 例から要約した好みと、明示ルールを比べる。要約で失われる例外や時刻のルールで差が出るかを見る。
3. **本物の属性認識**: VLMの `AttributeProvider` を実装し、信頼度が低い属性を「不明」として扱えば、未確定の仕組みが実際の認識の誤りに対して効くかを測れる。
4. **所有者・印（★）を属性として流す**: キーは開いているので、Unity や検出側から `owner`・`mark` を付ければ（必要なら `taxonomy.ATTRIBUTES` にも足してLLMに見せれば）、That's Mine の場面や家庭の入れ替え評価を同じ枠組みで再現できる。所有者の推定器と、「その物の所有者が頼んだときだけ」を表す変数の結び付けは、別途必要。
