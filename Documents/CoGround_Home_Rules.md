# CoGround 家庭ルールの設計ガイド

**対象シナリオ**　住人が「机の上のものを全部片づけて」と依頼する。ロボットは登録済みの家庭ルールに従って、各物体の扱いと収納先を決め、移動経路を計画する。実行中に人や環境が変化した場合は、必要な応答を取り、残りの計画を再評価する。

**位置づけ**　本書は研究プロトタイプの論理設計である。判定に使うデータ、判断を行う時点、結果の引き渡しを定める。実機の認識精度や停止性能は測定して初めて確定する。

## 背景と研究で扱う問い

机に陶器の皿Aと樹脂のコップBがある。「全部片付けて」と言われたロボットには、どちらも把持できる。しかし、この家では割れ物への接触が禁じられている。さらに、コップをつかめても、食器棚へ向かう途中に子供の遊び場があり、夕方にはそこへの進入が禁じられる。同じ「机に残った」という結果が、物体の扱い方からも、離れた場所での移動制約からも生じる。

家庭での物体利用について、ACKnowledgeは物理的な状況、人の状態、所有者が定める利用権などの対人関係を調べ、それらを計画に組み込んだ［3］。CoGroundが扱う問いは、住人が登録した取り決めを具体的な物体・場所・時刻に結びつけ、**計画のどこに効いたかを住人が確認し、必要な箇所を編集して結果を比較できるか**である。そこでルールの原文、機械が照合する条件、判定を支えた観測や予測を対応づける。

### なぜ Institutional Grammar を使うのか

「皿を上段に置け」と「皿を上段に置いてよい」は、物体・収納先・動作がすべて一致する。下段に置く案を退ける根拠になるのは前者である。また「18時以降、この辺りに入るな」には、効き始める時刻と禁止される境界通過が含まれる。住人が「19時からにして」と言う場合と、床を指して「この線まで」と言う場合では、変更すべきデータが違う。IG 2.0の成分を手掛かりにすると、こうした違いを登録時から保持できる［1］。

| 規制文を読む際の成分 | 本設計で保存するもの | 計画または編集での使い道 |
|---|---|---|
| Attributes（行為主体） | 家庭用ロボットに固定 | 依頼者や所有者は別の人物IDとして適用条件で参照できる |
| Deontic（規範の種類） | 義務・禁止・許可 | 満たすべき結果、避ける事象、選択可能な行為を区別する |
| Activation Condition（効く状況） | Scope。時刻、人物、依頼に関する条件など | 同じ経路にも進入時刻に応じた判定を返す |
| Object と Aim（対象と行為・結果） | 対象を選ぶ条件と、その対象について検査する内容 | 画像から「皿」を選び、配置結果の「上段」を検査する |

IGは制度文を分析するための文法である。ここではその区分を設計根拠とし、ルールを **原文 + 規範・条件・対象・内容** の4つの枠に分けて保存する（§4）。分ける目的は検索の高速化ではない。目の前の物体・場所・時刻と**照合できる形**にして、どの枠がどの判定を生んだかを住人に見せ、その枠だけを直せるようにすることである。Pereiraらは初期の制度文法を参照して規範を分散ロボット制御に結びつけたが、同研究の実装では振る舞いの同時実行を調整する独自の4演算子を採用した［2］。本設計で義務・禁止・許可を採る理由は、収納先を指定する発話、接触を避ける発話、条件付きで許す発話に異なる判定を与えるためである。

## 1．利用者から見た動作

18:10、机には割れ物の皿Aと樹脂のコップBがある。家には「割れ物に触るな」「18時以降、リビングで指定した範囲に入るな」「皿は上段、コップは下段」「子供の5 m以内にいる間は止まれ」という取り決めがある。

1. ロボットはAとBの両方を依頼の対象に含める。皿Aの収納先は上段と分かるが、持ち上げるには禁止された接触が必要なので机に残す。
2. コップBの収納先は下段である。棚への直行案では指定領域に入るため、ロボットはその外側を通る経路を探す。迂回案が成立すれば、コップBについて取得・運搬・配置を計画する。
3. 運搬中に子供が近づくと、台車は距離に応じた停止処理を行う。観測で停止を確認し、条件が続く間は発進を保留する。
4. 条件が解除されたら、現在地、把持状態、残経路、現在時刻を確認する。元の経路がまだ使えれば続行する。棚に置いたことが確認できた時点で「コップBを下段に収納済み」と記録する。
5. 住人には「コップは下段に収納しました。皿は割れ物に触れないという取り決めに従って机に残しました」と伝える。「全部」に対する未達成も説明の対象である。

## 2．構成と入出力

| 処理 | 主な入力 | 主な出力 | 責務 |
|---|---|---|---|
| ルール登録 | 発話、必要ならQuest上の指示範囲、登録者 | 構造化ルール、場所ID、対象条件に使う属性の定義、未解決・未対応の項目 | 原文の意味と参照先を保存する。語彙に無い内容は「未対応」として返す |
| 場面・タスク解析 | タスク指示、画像、地図、既知の物体情報、**ルールが使っている属性の一覧** | 対象の個体ID、目標、属性の値と根拠 | 「この机」「皿」などの参照先を決める。VLMには、ルールが使う属性だけを聞く |
| 計画 | 対象、現在状態、利用可能なスキル、ルール | 物体別の候補計画、保留理由、監視条件 | 触れてよいか、どこに置くか、どう到達するかを調べる |
| ルール評価 | ルール、具体的な対象、時刻付き予測または観測 | 判定、根拠、時刻・区間、不足情報 | 計画と実行で同じ意味の条件を評価する |
| 実行・監視 | 採用計画、監視条件、現在の観測 | 実行結果、停止・保留・続行・再計画要求 | 外部からの状態変化にも応答する |
| 説明・訂正 | 判定記録、原文、住人の訂正 | 理由の提示（**非該当の照合結果も含む**）、該当項目の更新、全ルールの再評価と前後の差分 | 属性の訂正・経路変更・例外許可を区別する |

**計画と実行の境目。** 計画側は「この予測と前提の下で実行できる手順」を渡す。実行側は「その前提が今も成立するか」を監視する。計画時に適合したルールでも、人や物の移動によって結論が変わるなら監視を引き継ぐ。

## 3．保存するデータ

| 保存単位 | 最小フィールド | 例 |
|---|---|---|
| ルール | ID、登録者、原文、規範、Scope、対象、指定内容。任意で理由・例外元ID | R2が zone_play への進入を禁止 |
| 場所 | ID、種類、表示名、座標系、形状または配置先情報 | Questで囲んだ床ポリゴン、棚の上段・下段 |
| 物体 | 個体ID、種類、既知の属性、値の根拠（VLM／住人／検出器）、観測時刻 | plate_A、割れ物、住人の登録による |
| 属性の定義 | 名前、見分け方、答えの選択肢、画像から判断できるか、使っているルール | fragile：落とすと割れる素材か／true・false／画像で判断できる／R1 |
| 関係 | 主体ID、関係、相手ID、根拠・更新時刻 | on(plate_A, table_01)、owner(cup_B, user_01) |
| スキル | 操作名、引数、必要条件、変えうる状態、完了の確認方法 | pick(x)には接触が伴い、成功後は把持状態になる |
| タスク記録 | 依頼ID、依頼者、候補、判定と根拠、予測／観測の区別、進捗 | 皿Aは接触禁止で保留、コップBは配置確認済み |

これらは論理的な保存単位であり、初期実装では同じデータベースやJSONで管理できる。属性の定義はルールと一緒に保存し、ルールバンクから集める（ルールを消せば、その属性も消える）。物体の属性は判明したものを保存する。属性が未登録なら照会結果を「不明」とし、必要時にVLMの観測や住人の確認で補う。箱に割れ物シールが見えたときは「シールを検出」と「家庭でその箱を保護対象に分類」を別々に記録できる。関係は「割れ物が中にある箱」のようなルールで参照する。

### VLMに何を聞くかは、ルールが決める

「割れ物かどうか」を判断するという発想は、割れ物についてのルールが無ければ生まれない。そこで、VLMへの質問を固定せず、ルールバンクから作る。

1. **登録時。** 「割れ物には触るな」を登録するとき、LLMは対象条件に使う属性（fragile）について、見分け方（「ガラスや陶器など、落とすと割れる素材か」）、答えの選択肢、画像から判断できるかを一緒に返す。同じ意味の属性がすでにあれば、その名前を使う（「壊れやすい物」と「割れ物」を別の属性にしない）。
2. **場面解析時。** いまあるルールが使っている属性のうち、画像から判断できるものを質問の一覧にしてVLMに渡す。VLMは物体ごとに、値と**根拠**（「材質：樹脂」）を答える。判断できなければ unknown と答える。
3. **ルールを足した後。** 前に見た物体は新しい属性を聞かれていないので、次に見えたときに解析し直す。聞いた属性が記憶にあれば、VLMは呼ばない。

どの物体にも聞く項目（種類、材質、見た目）は固定のまま残す。画像から判断できない属性（「パパの物」「形見」「高価な物」）はVLMに聞かず、住人が登録する。住人が登録した値はルールバンクのファイルに残し、再起動のあとも使う。画像から判断できる属性（割れ物、汚れ）を住人が訂正した場合は、その場の状態なので残さない。残した値は物体のIDで持つので、再起動のあとで同じIDが別の種類の物体に付いていたら使わない。同じ種類の別の物体に付いた場合は見分けられない（シミュレーションのように物体のIDが変わらない場合を前提とする）。その判断精度はVLMの性能の問題であり、本設計の範囲外とする（§10）。

## 4．ルール登録と形式

### 4つの枠

一つのルールは、**原文**と、次の4つの枠からなる。

| 枠 | 問い | R2の例 |
|---|---|---|
| 規範 $N$ | 義務・禁止・許可のどれか | 禁止 |
| 条件 $S$（Scope） | どの状況で効くか | 18時以降 |
| 対象 $T$ | どの物体・場所・行為者に関係するか | zone_play |
| 内容 $\phi$ | どの状態・変化を要求または禁止するか | 領域に入る |

以前の版にあった評価区間 $W$（計画や実行のどこを調べるか）と、状態ではなく変化を見る指定（transition）は、住人が選ぶものではない。「置く」は置き終わった時点、「入る」は台車が動く間、というように**内容ごとに決まっている**ので、内容の性質として語彙の側が持つ。そのため「領域に入る」と「領域の中にいる」は、引数の違いではなく別の内容である。

### 内容の語彙は、ロボットが変えられる状態から作る

内容を「進入の禁止」「接触の禁止」のような**ルールの種類**として数えると、種類の数がそのままシステムの限界になる。本設計では、種類を数えない。ロボットが自分の動作で変えられる状態を挙げ、**その状態のそれぞれについて内容を用意する**。規範（義務・禁止・許可）、条件、対象は内容と独立に組み合わせる。

| ロボットが変えられる状態 | 変えるスキル | 内容（語彙の名前） | 調べる時点 | 実行中の応答 |
|---|---|---|---|---|
| 台車の位置 | navigate | 領域に入る（enter_zone） | 台車が動く間。外から内への変化 | 避ける経路を計画し直す |
| 台車の位置 | navigate | 領域の中にいる（in_zone） | 台車が動く間。その時点の状態 | 避ける経路を計画し直す |
| 台車の速さ | navigate | 止まっている（base_stopped） | 全体 | 台車を止めて待つ |
| 台車の速さ | navigate | 速さが $v$ 以下（speed_below） | 全体 | 台車を止めて待つ |
| 触れている物体 | pick／place | 物に触る（contact） | つかむ時点 | つかむ前に保留 |
| 持っている物体 | pick／place | 物を持つ（holding） | つかむ時点 | つかむ前に保留 |
| 物体がある領域 | place | 領域に置く（placed_in） | 置き終わった時点 | 置く前に保留 |

主張は次の一点である。**ロボットが変えられる状態のすべてについて、住人が規範を書ける。** スキルが増えて変えられる状態が増えたら（吸引する、扉を開ける）、その状態についての内容を足す。網羅しているかは機械的に確かめられる（どの状態にも内容が1つ以上あること）。

同じ内容でも、規範が違えば別のルールになる。「上段に置け」は義務＋placed_in、「ごみ箱には置くな」は禁止＋placed_in、「頼まれたら触ってよい」は許可＋contact である。

### 条件

条件は、時刻の窓（from／until）、依頼者（「私が頼んだときだけ」）、そして状態についての条件を持つ。状態についての条件も語彙から選ぶ。

| 条件（語彙の名前） | 意味 |
|---|---|
| near_person | 人（子供／大人／誰でも）が台車から $d$ m 以内にいる |
| holding_something | ロボットが何かを持っている |
| base_in_zone | 台車が指定した領域の中にいる |
| region_full | 指定した領域に、その物を置く空きが無い |

条件は **AND** と **NOT** でつなげる。値は真・偽・不明の3値で計算する（偽 ∧ 不明 ＝ 偽）。OR は、ルールを2つに分ければ書けるので入れない。

「文房具は白い箱に。いっぱいだったら赤い箱に」は、対象が同じ2つの義務になる。

| | 規範 | 条件 | 対象 | 内容 |
|---|---|---|---|---|
| 1 | 義務 | NOT region_full(白い箱) | 文房具 | 白い箱に置く |
| 2 | 義務 | region_full(白い箱) | 文房具 | 赤い箱に置く |

満杯かどうかは、作業の順序どおりに、前の行までに置く物を数えたうえで、その物の置き場所があるかで決める。箱に属性 full があれば（VLMの答えか住人の訂正）、そちらを先に使う。

### 語彙の1件が持つもの

内容と条件は、語彙の登録簿に1件ずつ登録する。1件が、その語について必要なことをすべて持つ。

| 項目 | 役割 |
|---|---|
| 名前 | ルールに書く名前 |
| 読む状態 | 判定に使う状態の項目。未確定のとき「何が足りないか」を答えるのにも使う |
| 判定 | ある時点の状態から、真・偽・不明を返す関数 |
| 調べる時点 | つかむ時点／置いた時点／台車が動く間。内容だけ |
| 変化か状態か | 「入る」は外から内への変化。内容だけ |
| 実行中の応答 | 計画し直す／止めて待つ。内容だけ |
| 対象に取れる種類 | 物体／領域／ロボット。内容だけ |
| 説明の言い方 | 住人への説明に使う |
| LLMへの説明 | ルール登録のプロンプトは、登録簿から作る |

登録の検査、LLMのプロンプト、判定、実行中の監視、説明は、どれも登録簿を読む。**内容を1つ足すときに手を入れるのは、判定の関数と登録簿の1件だけ**である（§9の受入条件で確かめる）。

### 例

| ID | 住人の言葉 | 規範 | 条件 | 対象 | 内容 |
|---|---|---|---|---|---|
| R1 | 「Fragileなものを触るな」 | 禁止 | （常時） | fragile ＝ true の物体 | 物に触る |
| R2 | 「夕方6時以降は子供が遊びまわるから、リビングのこのあたりには入るな」 | 禁止 | 18時以降 | zone_play | 領域に入る |
| R3a・R3b | 「皿は食器棚の上段に、コップは下段に」 | 義務 | （常時） | 皿／コップ | 上段／下段に置く |
| R4 | 「子供の5 m以内にいるときは止まれ」 | 義務 | near_person(子供, 5 m) | ロボット | 止まっている |

R2の「子供が遊ぶから」は説明用の理由であり、判定には使わない。R3は原文を共有する2レコードである。

~~~json
{
  "id": "R2",
  "original_text": "夕方6時以降は子供が遊びまわるから、リビングのこのあたりには入るな",
  "norm": "prohibition",
  "scope": {"clock": "home_local", "from": "18:00", "until": null},
  "target": {"kind": "zone", "id": "zone_play"},
  "requirement": {"predicate": "enter_zone"},
  "reason": "子供が遊びまわるため"
}
~~~

以前の書き方（predicate ＝ footprint_overlaps、window、transition を書く）で保存したルールも、同じ判定で読める。

「このあたり」は登録時にQuestで指定した領域に結びつける。ロボットの地図と同じ座標系に変換して判定する。本例の18:10は発話が明示した夕方として扱う。日をまたぐ有効期間は未指定なので、解除時刻を勝手に補わず、翌朝の運用には別途確認を要する。

「私が指示したときだけ触ってよい」は、登録者を「私」の参照先として保存し、依頼者がその人物と一致するときに限って該当する接触禁止への例外を有効にする。例外には対象、行為、元の禁止ID、有効期間を持たせる。共有端末で依頼者を特定できなければ、例外の成立は未確定とする。

### 語彙に無いことを言われたとき

「静かに運べ」「丁寧に扱え」「先に皿を片づけろ」のように、語彙のどの内容・条件でも書けない発話は、近い内容で代用しない。ルールにせず、**「未対応」として、理由と、書ける内容の一覧を返す**。引数が足りない（速さの上限が無い）、対象の種類が合わない（物体に「入る」）場合も同じである。黙って落としたり、似たルールにすり替えたりすると、住人は「登録できた」と誤解する。

## 5．状態・イベント・照合

計画では時刻付きの予測状態列 $\tau_\pi$、実行では観測状態列 $\tau_{\mathrm{obs}}$ を使う。述語 $p(t,b)$ は、割当 $b$（対象の個体や領域）について真・偽・不明のいずれかを返す。イベントは述語の変化として扱える。

$$
\uparrow p(t)=\neg p(t^-)\land p(t),\qquad
\downarrow p(t)=p(t^-)\land\neg p(t).
$$

$p$ を「車体が指定領域と重なる」とすれば、内容「領域に入る」は $\uparrow p$、内容「領域の中にいる」は $p$ である。経路の両端が外でも途中で横切れば進入になるため、判定には経路と領域境界の交差を使う。すでに領域内で18時を迎えた場合、「入るな」だけからは退出義務は発生しない。「中にいるな」なら違反になる。

### ルールを絞り込まず、全部を照合する

以前の版は、スキルが変える項目とルールが読む項目の共通部分で、再評価するルールを絞り込んでいた（$\mathrm{Candidates}(a)$）。これはやめる。Fetchのスキルは navigate・pick・place の3つしかなく、スキルを鍵にしてもルールはほとんど絞れない。家庭のルールは数十件であり、全件を評価しても計算は一瞬で終わる。

重要なのは検索ではなく**照合**である。ルールの対象（「fragile ＝ true の物体」）と、目の前の物体の属性（「この皿は fragile ＝ true」）を、同じ語彙で突き合わせて、「この物体はこのルールに該当する」と言えることが要る。文字列の一覧のままでは、これが毎回LLMの解釈に依存する。

- **計画時。** 対象の物体ごとに、物体が対象のルールをすべて見る。内容が決めている時点（つかむ時点／置いた時点）の予測で判定する。収納先を決める義務は、**条件と対象の両方**に合うものから選ぶ。
- **実行時。** 台車が動く間に調べる内容のルールと、条件が台車の位置・速さを読むルールを、すべて監視にする。人の移動、時計、対象の変更でも判定し直す。
- **訂正時。** 属性・領域・ルールを直したら、依頼の全行について全ルールを評価し直し、**訂正の前後で変わった行と項目だけ**を差分として返す。差分が小さいことは、絞り込みの結果ではなく、評価し直した結果として示す。

ルールが読む項目の対応（依存関係）は残すが、用途は「この訂正はどのルールに関係するか」を住人に示すことと、未確定のときに足りない事実を答えることに限る。

**他タスクへの適用。**「カーペット上では吸引しない」なら、吸引状態をロボットが変えられる状態に足し、内容「吸引している」を1件登録する。条件 base_in_zone(カーペット) と組み合わせれば、吸引しながら乗る場合も、乗ったまま吸引を始める場合も同じルールで検査できる。

## 6．適用、違反、未確定

対象 $b$ と時刻 $t$ における適用条件は $A_i(t,b)=S_i(t,b)\land T_i(t,b)$。有効な例外は対象を照合してから元の禁止の適用範囲を狭める。次式ではその処理後の $A_i$ を用いる。

$$
V_i(\tau,b)=
\begin{cases}
\exists t\in W_i:\ A_i(t,b)\land\phi_i(t,b) & \text{禁止}\\
\exists t\in W_i:\ A_i(t,b)\land\neg\phi_i(t,b) & \text{維持義務・指定時点の義務}
\end{cases}
$$

ここで $W_i$ は、内容 $\phi_i$ が決めている「調べる時点」である（§4。住人は書かない）。

許可された行為を選ばなくても違反は生じない。適用対象がなければ「非適用」。違反の証拠があれば「違反」。評価範囲について適合を確認できれば「適合」。足りない観測によって結論が変わるときは「未確定」とし、不足項目を返す。先の時点について得た適合判定には「予測」を付ける。物体を計画から省略すれば接触違反を回避できても、片付けの達成件数には算入しない。

### 非該当も見せる

VLMの答えは間違うことがある。厄介なのは、**自信を持って間違えた**場合である。割れ物の皿を「割れ物ではない」と答えると、R1は「非適用」になり、何の警告もなく皿をつかむ計画ができる。未確定なら保留になるが、誤った確定は黙って素通りする。

そこで、物体ごとに、対象の条件との照合の結果を、**合わなかったものも含めて**見せる。

> 皿A：fragile は false（VLMの判断）なので、「割れ物には触るな」は当てはまらない。

値の出どころ（VLM／住人／検出器）は照合結果に付く。VLMが答えた根拠（「材質：樹脂」）は、場面解析の結果に物体ごとに残る。

住人はこれを見て、認識が間違っていると気づき、その場で属性を直せる（「この皿は割れ物」）。住人の訂正はVLMの答えより優先し、次の場面解析のあとも効く。直すと全ルールを評価し直し、変わった行（皿A：運ぶ予定 → 保留）を差分で返す。認識の誤りを無くすことは本設計の目標ではない。**誤りが見え、すぐ直せて、直した結果がどこに効いたか分かる**ことを目標とする。

### 同じ式を片付けの場面に当てはめる

| ルール | 適用条件と対象 | いつ、何を見れば判断できるか |
|---|---|---|
| R1 | $T(x)=\mathrm{Fragile}(x)$、常時 | 接触を伴う候補を評価する。割れ物属性が不明で、把持に接触が必要なら保留 |
| R2 | $S(t)=\mathrm{Evening}(t)$、$T(z)=[z=\mathrm{zone\_play}]$ | 移動中に車体が領域の外から内へ移る時刻に、時間条件が有効かを評価 |
| R3a/b | 収納を計画する皿／コップ | 配置完了時の位置を評価。皿は上段、コップは下段。片付けを見送った個体は依頼の未達として記録 |
| R4 | 一人以上の子供がロボットから5 m以内 | 条件が成立している各時点で台車の停止を確認。子供側の移動でも再評価 |
| 許可の例 | 指定した依頼者・対象・依頼ID | 指定した禁止に対する今回の把持例外として評価。食器棚の位置や禁止経路は別途照合 |

時間順序を追加する際には、上の状態列に時間論理を適用できる。例えばR4をLTL風に書けば $\mathbf G(\mathrm{NearChild}\rightarrow\mathrm{BaseStopped})$ であり、$\mathbf G$ は評価区間を通じた成立を表す。R3は配置完了時に評価するため、取得直後に皿がまだ上段にないことは違反にならない。「18時」「5 m」は時計・幾何計算が返す述語の入力である。

## 7．計画から実行への引き渡し

計画結果には**手順、成立の前提、監視項目、条件成立時の応答、再計画の契機**を含める。監視は、初期評価時・次の動作の直前・実行中に行う。

| ルール | 計画時の判断 | 実行時に見るもの | 応答 |
|---|---|---|---|
| R1 接触禁止 | 取得に必要な接触と対象属性 | 個体の取り違え、属性訂正 | 接触前に保留・確認 |
| R2 時間付き進入禁止 | 取得時と運搬時の予測経路・境界通過時刻 | 遅延、経路変更、現在位置 | 進入前に待機し、別経路を探す |
| R3a/b 収納先 | 対象の種類と指定段の対応 | 棚の利用可否、実際の配置先 | 配置前に確認。所定の段への配置後に完了記録 |
| R4 近接時の停止 | 予測できる接近には待機・迂回を入れる | 人と台車の位置・時刻、台車の実速度 | 停止要求、停止確認、近接中の発進保留 |

R4の意味は $\mathrm{NearChild}(t)\Rightarrow\mathrm{BaseStopped}(t)$。近接は「少なくとも一人の子供との距離が5 m以下」とする。5 mは発話中の指定値である。停止要求を送った時刻、実停止した時刻、観測した距離を区別する。進入時点ですでに停止していることを求める実機実装には、距離の測定基準、速度、観測・制動遅延を含む予測と検証が必要になる。計画通過後も監視し、距離の観測が失われた場合に発進・続行を許すかは応答方針に明記する。本設計例では近接解除を確認できるまで発進を保留する。

## 8．擬似コード

以下は制御の分担を示す。経路探索、物体認識、停止制御は各モジュールが提供する。

~~~text
PLAN(request, state, rules):
    targets = ground_targets(request, state)       # 机上の全対象を保持
    result = initialize_rows(targets)
    for x in targets:
        facts = attributes_used_by_rules(x, rules, state)  # VLMに聞くのは、ルールが使う属性だけ
        result.record_judgments(x, match_targets(x, rules, facts))   # 非該当も残す
        dest = resolve_destination(x, request, rules, facts)         # 条件と対象の両方に合う義務
        touch = evaluate_at_grasp(x, all_rules_about_objects(rules), facts)
        result.record(x, touch, dest)
        if touch is forbidden_or_unknown or dest is unresolved:
            result.defer(x, reason_and_missing_facts())
            continue

        for option in candidate_plans(state, x, dest):
            # 取りに行く → つかむ → 運ぶ → 置く
            trace = predict_states_and_times(option, state)
            verdict = evaluate(trace, rules, x, option.affected_entities)
            if verdict.contains_violation_or_blocking_unknown:
                result.record_rejection(x, option, verdict)
                continue
            result.schedule(x, option, verdict.assumptions,
                            build_monitors(option, rules))
            state = trace.end
            break
        if not result.is_scheduled(x):
            result.defer(x, search_evidence())
    return result

EXECUTE(plan, world):
    install_monitors(plan)
    while plan.has_remaining_work():
        update(world, observations_and_clock())
        decision = evaluate_current_and_imminent_conditions(world, plan)
        if decision.requires_immediate_response:
            apply_response_and_verify(decision)    # 例：停止要求と実停止確認
            monitor_during_hold_until_resolved()
            update(world, latest_observations())
            if not revalidate_remaining(plan, world):
                plan = replan_unfinished_work(world, plan.goal)
                replace_monitors(plan)
            continue
        if decision.lacks_required_evidence:
            hold_affected_operation_and_request_evidence()
            continue
        advance_current_step_with_monitoring()
        if step_completion_observed():
            verify_postcondition_and_record()
    return observed_outcomes_and_unfinished_items()
~~~

実行の途中から再計画する場合は、すでに持っている物、完了した収納、未達成の依頼を引き継ぐ。候補が見つからない場合は、探索した区間・課した制約・上限を記録する。ある制約を課して探索に失敗しただけで、失敗原因をその制約に断定しない。

**最小デモの実装範囲。** 既知の棚・指定ゾーン、対象物への意図した接触、台車経路、配置結果を扱う。隣接物に腕が触れるような副作用まで検出する段階では、腕・搬送物の軌道と周囲物体の状態を評価対象に加える。ユーザーの訂正では、全ルールを評価し直し、訂正の前後で変わった行と項目を差分として返す（無関係な取り決めの判定は変わらないことが、差分で確かめられる）。

**完成の基準。** 上の表の各行が自動テストで通ること。7つの内容がすべて登録でき、判定できること。内容を足すときに手を入れるのが、判定の関数と登録簿の1件だけであること。語彙に無い発話に「未対応」を返すこと。



## 10．対応範囲と限界

本設計が扱うのは、**ロボットが変えられる状態について、観測できる条件の下で、要求または禁止する**ルールである。次のものは扱わない。

| 扱わないもの | 例 | 理由と扱い |
|---|---|---|
| 測れない様態 | 「静かに」「丁寧に」「そっと」 | 真・偽を返す状態が無い。登録時に「未対応」を返す。速さの上限など、測れる量に言い換えれば書ける |
| 順序・回数 | 「先に皿を」「一度に2つまで」 | 内容は1時点の状態か、その変化である。作業の順序は、住人がシーケンスの編集で指定する |
| 好み・重み | 「できれば上段に」 | 義務・禁止・許可の3つだけを扱う。違反の度合いは比べない |
| 例からの学習 | 片付け方を見せて覚えさせる | ルールは住人の言葉から登録する。観察からの獲得は別の研究課題である |
| 画像から分からない属性 | 「パパの物」「形見」「高価な物」 | VLMには聞かない。住人が物体に登録する。認識の精度はVLMの性能の問題であり、本設計の外にある |
| 腕や搬送物の副作用 | 隣の物に腕が触れる | 意図した接触だけを見る（§9の最小デモの範囲） |

実装上の制約もある。

- 「速さが $v$ 以下」を破りそうなときの応答は、減速ではなく停止である（止まれば上限は守れる）。減速する応答は用意していない。
- 「何かを持っているとき」は、実行中はロボットの把持状態から分かる。動作計画の段階では区間ごとの把持状態を渡していないので、この条件を持つルールは計画時に未確定になり、安全側に保留する。
- 「満杯」は、箱の属性 full か、置き位置の空きの計算で決める。物が重なってよい入れ物（ごみ箱など）は、属性が無ければ満杯にならない。
- 条件のORは入れていない。ルールを2つに分けて書く。
